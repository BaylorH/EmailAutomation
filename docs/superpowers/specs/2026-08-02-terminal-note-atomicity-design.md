# Terminal Note Atomicity Design

**Status:** Approved for autonomous execution under the existing SiteSift production-readiness mission.

**Deliverable:** code

## Goal

Make a `property_unavailable` / requirements-mismatch transition recoverable and fail-closed: the system may not move or finalize a row, mark the event handled, or send its terminal acknowledgement unless the reason is durably present in the campaign Sheet. Once terminal processing starts, retries must also use the exact original message, reason, note, event, row/anchor, response scenario, and response body rather than fresh model output.

## Reproduced Root Cause

`process_inbox_message` currently moves the row and finalizes Firestore thread state before attempting the Notes/Comments write. That write is wrapped in a nested catch that logs and continues. A missing notes column or Sheets failure therefore produces the exact customer-visible split state: a correct terminal reply and stopped/non-viable row with no durable reason.

## Commit Protocol

Google Sheets and Firestore cannot share one transaction, so this transition is a small idempotent saga:

1. Run the earlier ordered informational and `new_property` handlers first. Create the terminal saga only when the applicable `property_unavailable` handler is reached, so a failure in an earlier handler cannot strand a terminal saga for work that never started.
2. Build one immutable saga from the original source message and proposal. It includes the exact source identities, reason, merged terminal note, event key, source row/anchor, response scenario/body, recipient, and a bounded finalization plan naming every terminal root and row shift.
3. Preview the divider and enumerate the exact Firestore writes without mutating the Sheet. More than 500 planned writes fails before any Sheet mutation.
4. Claim the lexicographically canonical root from the persisted plan in a Firestore transaction, increment its durable fencing counter, then persist the immutable saga on the winning current root and a saga pointer plus follow-up stop on every exact source-row root in that same transaction. The in-memory execution contract carries the unique owner plus fencing token. Concurrent split-root sources yield one immutable winner; an unexpired foreign execution lease is never stolen, even if a stale reply-attempt envelope exists.
5. Before any terminal Sheet write, the current fenced owner transactionally persists one version-2 `terminalSheetMutationAttempt`: mutation kind (`move_with_note` or `ensure_note`), source/final row, row anchor, note hash, attempt ID and ordinal/lineage, exact saga key/hash, owner/fencing token, `request_started` status, and a provider deadline that is strictly shorter than the canonical execution lease. `attemptImmutableHash` covers exactly those immutable identity fields, including `version: 2`; `attemptHash` separately covers the complete exact persisted attempt state except `attemptHash` itself, including `attemptImmutableHash`, status, and every status-specific outcome. Exact schemas reject missing, extra, cross-status, malformed-type, timestamp, outcome, or fence fields even when an attacker recomputes both hashes. Once `request_started` exists it is non-stealable: a newer owner may only read and reconcile Sheet evidence. If the exact planned row plus exact note effect is present, the newer owner may record `reconciled_applied` under its fence and continue; absent, partial, or unreadable evidence records one hash-rotating `needs_operator_review` transition and permits zero additional Sheet mutations. An exact replay of the same state is a no-op. An explicit provider status whose type is exactly integer and whose value is exactly `429` is the one definitive non-acceptance lane: the current owner durably records `definitely_not_applied`, and only a different owner with a strictly higher fencing token may create the next ordinal linked to that attempt's final full-state `attemptHash`. The same owner cannot consume a second permit, timeout/5xx ambiguity can never create a next ordinal, and at most eight attempts are retained before failing closed for operator review. Version-1 active attempts, histories, and archived settlement evidence fail closed without migration or dual-read behavior. This narrows the cross-provider ambiguity window but does not claim atomicity between Firestore and Google Sheets.
6. The first owner commits the destination-row copy, merged terminal note, and source-row deletion in one ordered Google Sheets `batchUpdate` only after the mutation attempt is durable and its provider deadline is still inside the lease. Missing column, read failure, or batch failure is fatal and retryable. Ambiguous apply-then-raise is resolved only by exact readback; it is never blindly replayed.
7. Finalize only the roots and row shifts named by the persisted plan. One Firestore transaction reads and validates the canonical saga key/hash, exact owner/fencing token, and future lease, renews that lease, then writes stopped/non-viable state and creates durable notification/reply obligations on the current root. Stale owner A may never finalize after owner B acquires a higher fence. It does not mark the event handled or claim that a reply succeeded.
8. Renew and verify the exact saga key/hash, owner, fencing token, and well-formed unexpired lease before creating the idempotent operator notification. Persist the handled-event marker and clear the notification obligation only in a transaction that re-verifies that fence.
9. Settle the reply from the persisted body and recipient. Persist every send/queue intent in an owner-fenced transaction and renew immediately before Graph or pending-queue effects. Recovery uses only exact retained proof: provider-reachable attempts with a retained permit in `request_started`, `accepted`, or `needs_reconciliation` reconcile Sent Items by that permit's immutable draft ID and frozen envelope, never by heuristics. A `queueing_response_retry` attempt performs zero Sent lookup and proceeds only with its retained `settled_definitely_not_sent` permit plus exact pending evidence. A `queueing_campaign_suppression` attempt is provably pre-send, carries no permit, verifies that no active Graph permit exists, and also performs zero Sent lookup. Partial, missing, mismatched, or unsupported state fails closed. An exact Sent match atomically records `sent_reconciled` and removes only exact pending work. If Graph accepted the send but a newer owner acquired the expired lease before outcome persistence, the stale owner cannot queue, write an outcome, or clean up; the newer owner reconciles Sent Items without another send. Queue outcomes and final saga cleanup are likewise transactionally fenced. Clear the reply obligation only for a durable sent/indexed, sent/unindexed reconciliation, exact queued retry, recipient-suppressed, or campaign-stopped outcome.
10. Before removing active saga pointers, transactionally append an immutable, exact-source-bound projection to `terminalSettlements`. Each hashed tombstone contains its settlement ordinal, saga key/hash, Graph and Internet source identities, final row, notification/reply outcomes, settlement timestamp, and the final Sheet attempt plus its bounded linked history and review evidence. The list retains at most eight exact generations; reaching the limit fails closed for operator review and never evicts an older tombstone. Exact-source delivery scans and validates this collection before replacement or generic admission and exits as deliberately settled without effects even when the inbox processed marker was not written.
11. Remove saga pointers only after both obligations are resolved and that generation's settlement projection is durable. In the same cleanup transaction, clear the active `terminalSheetMutationAttempt`, `terminalSheetMutationHistory`, and `terminalSheetMutationReview` fields so a legitimate later terminal generation starts with a fresh ordinal-one attempt; client completion follows reply settlement. Ambiguous cleanup commits require strict readback of every planned exact root plus canonical claim, current obligations, active saga/Sheet pointers, and the exact source-bound settlement before success may be inferred. Later generation B appends independently without invalidating generation A, and retries of either source must find only their own tombstone.

On retry after either the Sheet batch or Firestore finalization committed ambiguously, the exact source message may bypass generic processed/manual/campaign gates, loads the persisted saga before blank-body, attachment, URL, order-log, fresh Sheet/client/identity, model, or generic-event work, and resumes from frozen stored evidence. Fresh client Sheet, tab/Notes layout, row anchor, or recipient drift cannot redirect it. A different later message persists and verifies only its exact history/index/timestamp/envelope, remains retryable, and stops before campaign, status, client, follow-up, or other downstream work. If exact recovery fails inside a same-thread scanner batch, every later message remains unprocessed and neither source receives a processed marker. An idempotent note helper validates or repairs the exact stable note before state finalization, and the pending-terminal fields keep every staged root follow-up-ineligible throughout a partial failure.

## Stable Note Identity

The human-readable note remains the current format produced by `_build_property_unavailable_comment`, including truthful requirements-mismatch language and alternate-property context. Its date comes from `receivedDateTime` (falling back to `sentDateTime`, then UTC now only for legacy messages without either timestamp), so a retry on another day does not create a second note.

The move helper uses the zero-based notes column in an `updateCells` request between its existing copy and delete operations, so columns beyond `Z` and punctuation in tab titles do not require A1 conversion on the normal path. The already-below repair path uses safe A1 construction. Inside the terminal provider window, the Sheets wrapper installs a concrete transport timeout and disables generic 429/5xx replay. A later fenced processing retry follows only the explicit definite-429 lineage above or reconciles an ambiguous result by exact readback.

## Terminal Sheet Attempt v2

The attempt state machine has five exact persisted shapes. `request_started` has no outcome fields. `applied`, `reconciled_applied`, `needs_operator_review`, and `definitely_not_applied` each have one exact outcome schema with validated booleans, non-empty evidence/error strings where required, timezone-aware `datetime` timestamps, and owner/fencing identities. Version, ordinal, row, fence, and provider-status integers require the exact integer type: booleans and numerically equal floats are invalid. Mutation kind is centrally derived from immutable saga geometry: `ensure_note` if and only if `sourceRow == finalizationPlan.finalRow`, otherwise `move_with_note`; a valid-enum kind flip fails even when every attempt and projection hash is recomputed. A staged saga must not contain the mutable `finalRow` field, while a finalized saga must contain the exact planned final row. Caller-kind disagreement and phase/row-shape drift fail before attempt persistence or provider work, and provider branching uses only the derived kind. A state transition is constructed from immutable identity again, rather than merging into the prior dict, so review or provider fields can never leak into a later status.

The only legal cross-state transitions are:

- `request_started -> applied | reconciled_applied | needs_operator_review | definitely_not_applied`
- `needs_operator_review -> reconciled_applied`

An exact same-state replay performs no write and does not rotate a timestamp or hash. `applied`, `reconciled_applied`, and `definitely_not_applied` are terminal; every other transition or outcome rewrite fails closed. Visible review evidence binds to the exact attempt ID and the post-transition full-state hash. A legitimate review transition rotates the full hash once, its exact replay preserves both attempt and review, and reconciliation clears the review while stripping every prior review field.

Every history entry must be a version-2, exact-429 `definitely_not_applied` final state. Ordinals are contiguous, attempt IDs are unique, each owner differs from its predecessor, fencing tokens strictly increase, and `previousAttemptHash` equals the predecessor's final full-state `attemptHash`. Settlement tombstones recursively validate the same rules. There is no v1 request-path migration, lazy migration, or dual read.

Firestore transaction ambiguity is accepted only when readback equals the complete intended attempt, claim renewal, history, and review state. Apply-then-raise can therefore reconcile the exact intended bytes/state, while no-apply or a different fabricated but internally hash-valid state remains retryable. An exact no-apply leaves attempt, history, and review unchanged so the next invocation may create the intent; the wrapper writes operator-visible review evidence only after a read-only classification finds genuinely malformed persisted Sheet state, never for an empty ambiguity or a valid claim/owner rejection. Finalization validates the complete active attempt lineage before writing any terminal root.

## Exact Graph Envelope and Identifier Proof

Every provider-reachable permit freezes the raw source message identity and the complete prepared draft envelope before `/send`: the case-sensitive subject, canonical HTML-body hash derived from visible text without lowercasing user-visible content, exact To/Cc recipient sets, required empty Bcc set, and canonical attachment multiset. Exact-Sent settlement hydrates sparse Graph records when necessary and must prove every frozen field against the immutable draft ID; subject-prefix normalization, heuristic body matching, and partial recipient or attachment evidence are not authority. Raw Graph message IDs remain unchanged in evidence and hashes, while one shared path encoder percent-encodes each ID exactly once at every Graph URL boundary.

Permit issuance itself is a durable local protocol. A deterministic issuance attempt binds issuer path, thread, client, source message, envelope, owner, and fence before a capability becomes usable. No-apply retries remain eligible to issue once; apply-then-raise recovers the exact committed permit without issuing or sending again; repeated exact recovery is stable; and missing, malformed, linked, or lookalike state fails closed before provider work. The same rules cover pending-response and terminal-saga issuers.

## Post-settlement Client Completion

Deleting exact pending work after a proven send is not the end of the transaction. Direct accepted sends, automatic immutable-Sent reconciliation, and authenticated operator exact-Sent reconciliation must each create exactly one deterministic user-root `pendingResponseCompletionObligations` document in the same Firestore commit that settles the retained permit and deletes its exact pending issuer. The version-1 obligation has an exact schema and immutable hash over user, client, thread, pending document, source Graph message, pending-envelope hash, permit ID/hash, exact-Sent evidence hash, and a strict boolean `completeClientAfterReply`. The completion flag is exactly equivalent to whether the canonical client binding is nonempty: client-bound work records a nonempty client plus `true`, while supported clientless queue work records an empty client plus `false`. A client-bound replay also requires the thread root to contain the exact same string client ID; a clientless replay does not gain a completion obligation from an unrelated thread client field. Settled outcomes preserve the same equivalence: `true` permits only `client_completed` or `client_ineligible`, while `false` permits only `not_required`. The CAS authority validates the canonical path and complete freshly owed payload, reads every required document before its first write, rejects arbitrary or extra side documents, and accepts an apply-then replay only when the retained permit, exact Sent evidence, deleted pending issuer, and owed-or-settled completion tombstone all match.

Pending processing begins with a server-side `status == "owed"` query capped at 501 records, so retained settled history cannot starve new work. Before any local completion effect, replay revalidates the obligation schema/hash/path, exact user/thread/client/permit/envelope/Sent linkage, settled permit state, and absence of the original pending document. It performs no Graph request, Sent Items lookup, queue send, provider deletion, or heuristic reconciliation. A completed client settles `client_completed`; stopping, stopped, archived, or deleted clients settle `client_ineligible`; a false obligation settles `not_required`; and a still-live client remains owed unless `_maybe_mark_client_completed` returns true or a status re-read proves completion. Settlement is another read-before-write transaction and retains the immutable tombstone.

System health uses the same server-side owed-only bound and exact active-record validation. Owed work degrades health, malformed or over-bound active work fails health closed, and retained valid settled tombstones do not count as backlog. Terminal completion remains bound to the immutable terminal settlement projection: if the initial post-cleanup local completion returns false, the invocation is retryable and the exact source tombstone later retries only that local effect.

## Required Invariants

- A terminal-note batch failure commits neither the row move nor the note and occurs before Firestore terminal finalization, event handling, or outbound reply.
- A missing Notes/Comments column fails closed and records a retryable processing failure.
- Reprocessing an already-written note does not duplicate it.
- An already-below row cannot be finalized or marked handled without the durable note.
- Requirements mismatch never gets described as property unavailability.
- The terminal plan is persisted before Sheet mutation and cannot exceed Firestore's 500-write batch limit.
- Original saga inputs cannot drift on retry; a hash mismatch fails retryably.
- All exact source-row roots remain follow-up-ineligible after saga staging, including on failure.
- Finalization creates explicit notification/reply obligations; handled state is written only after the notification, and the source remains unresolved while a reply is owed.
- Only the exact source message can resume a stopped terminal saga without fresh model output.
- A different source on any staged/finalized saga root is history-only and retryable; it cannot reactivate the thread or reach attachments, Sheet lookup/mutation, order logs, model work, events, notification, queueing, or reply.
- An exact recovery failure blocks later same-thread batch admission and leaves both exact and later processed markers absent.
- Active canonical execution leases are honored until expiry regardless of any current or stale reply-attempt envelope.
- Every execution mutation validates the immutable saga key/hash plus exact owner/fencing token and a parseable future lease; a missing, malformed, expired, or superseded fence fails closed.
- Send/queue intent writes, notification/reply outcomes, and final cleanup transactionally re-read the canonical claim, so stale worker A cannot mutate or clear worker B's newer claim.
- Failure to read the authoritative thread root is retryable before exact/pending classification or generic effects; an empty fallback root is forbidden.
- Provider-reachable attempts reconcile only by retained immutable draft ID plus the frozen envelope. Definitely-unsent response queues and provably pre-send campaign queues perform zero Sent lookup and require their respective retained-permit or no-permit proof; malformed or mixed states fail closed.
- Pending workers transactionally read the thread and pending document immediately before Graph and skip on the fail-closed union of `terminalSagaKey`, `terminalReplyOwed`, `terminalNotificationOwed`, `pendingTerminalReason`, a `terminalSaga` dict, a `terminalSagaClaim` dict, or a `terminalReplyAttempt` dict. Historical outcomes and `terminalSettlements` do not block legitimate post-cleanup work. Pending workers claim only unchanged work with no active or malformed foreign lease.
- A pending worker that claimed early must transactionally re-read the exact token, unchanged immutable envelope/body, future claim lease, and terminal-free thread immediately before Graph. If terminal staging won the race, it releases only its own exact claim and sends nothing; stale tokens cannot clear, delete, or mutate replacement work.
- Definitely-unsent and campaign-suppressed queue intents reuse only an exact deterministic pending-response document; the response-retry lane requires a retained `settled_definitely_not_sent` permit, the campaign lane requires no retained or active permit, and immutable saga-body/attempt drift or mismatched evidence fails closed without overwrite.
- A `request_started` terminal Sheet attempt is non-stealable and recovery is read-only until exact applied evidence. Only a definite 429 may create a linked next attempt, and only for a different owner with a strictly higher fence; ambiguous timeouts/5xx and same-owner retries remain zero-mutation.
- Terminal Sheet attempts are v2-only and have separate immutable-identity and full-state hashes. Exact status schemas and legal transitions fail closed on missing, extra, cross-status, malformed, or rewritten outcomes.
- Every terminal Sheet attempt binds mutation kind to immutable saga geometry: equal source/final rows require `ensure_note`, while different rows require `move_with_note`.
- Caller-kind disagreement and staged/finalized saga phase-shape drift fail before terminal Sheet attempt persistence or provider work.
- An ambiguous no-apply attempt-creation commit leaves no orphan review and cannot poison the next exact invocation.
- Sheet lineage links only final full-state hashes, uses unique attempt IDs plus strictly increasing distinct-owner fences, and recursively rejects v1 or tampered active/history/tombstone state.
- Ambiguous attempt transactions reconcile only exact intended attempt, history, review, and claim-renewal readback; a different valid hash/state is not accepted.
- Finalization is one owner-fenced Firestore transaction; ambiguous cleanup is accepted only after exact all-root/claim/obligation/settlement readback.
- A bounded source-bound settlement collection preserves up to eight immutable terminal generations without eviction. Every projection archives Sheet attempt/history/review evidence, active Sheet fields clear atomically during cleanup, and retries of generations A and B resolve to their own tombstones without generic work.
- Blank-body exact retries and campaign paused/stopped settlement still use the immutable saga, frozen Sheet coordinates, and frozen recipient.
- No customer campaign, production flag, mailbox send, or external contact is part of this fix or its tests.

## Test Boundary

Extend the existing full `process_inbox_message` harness in `tests/test_compound_nonviable_processing.py`; do not prove only a detached helper. The harness must expose the note cell, move/finalization calls, handled events, reply calls, and staged Firestore roots.

Required red-green cases:

1. Atomic Sheet batch rejection: retryable error; neither note nor move commits; no Firestore finalization, handled event, or reply; all roots staged non-sendable.
2. Missing Notes/Comments column: same fail-closed outcome.
3. Successful Sheet helper contract: one batch contains insert, copy, note update, and delete; existing notes are preserved and the terminal note is appended once.
4. Already-below retry/legacy row: note is ensured idempotently before finalization; a note failure prevents handled state.
5. Requirements-mismatch full path: truthful note text is persisted.
6. Source-keyed recovery: no-event, changed-reason, and changed-alternate retries preserve the original note and response.
7. Ambiguous finalization: apply-then-raise leaves both obligations durable; only the exact source resumes and settles them once.
8. Notification ordering: no notification exists before finalization, and handled state remains absent while notification persistence fails.
9. Plan bound: a transition requiring more than 500 Firestore writes fails before divider, move, note, notification, or reply mutation.
10. Persisted saga tampering: changed immutable payload fails before model, Sheet, notification, or reply work.
11. Provider-accepted reply ambiguity: an owed-clear failure retries through Sent Items and never sends or queues again.
12. Definite-unsent queue ambiguity: a retained definitely-not-sent permit may atomically create the exact deterministic pending document; recovery then settles `queued_retry` with zero Sent lookup, send, or requeue, while missing permit proof or mismatched message/recipient/client/body evidence fails closed.
13. Narrow exact recovery: blank bodies and URLs/attachments still skip fresh client/Sheet lookup, attachment/link work, order logs, model calls, and generic events.
14. Frozen context: fresh client Sheet or recipient drift is ignored; tab, Notes-column, row-anchor, and immutable-hash drift fail closed.
15. Campaign settlement: stopped campaigns persist `campaign_stopped`; paused/maintenance campaigns persist queue intent before deterministic pending work and recover an ambiguous owed-clear without sending.
16. Canonical split-root race: two concurrent current roots transact on one plan-derived claim root and yield one winner and one retryable loser.
17. Lease ownership: a stale reply-attempt envelope cannot override an unexpired foreign canonical lease.
18. Different-source admission: staged/finalized roots save later sources for history only, leave them retryable, perform no downstream work, and still allow the exact source to recover.
19. Scanner batch isolation: failed exact recovery does not process a later same-thread message and writes neither processed marker.
20. Canonical fencing interleave: stale owner A cannot queue, persist an outcome, or clean up after owner B acquires a higher fence; an accepted Graph send is reconciled by B with exactly one provider send.
21. Lease validation: owned claims with missing, malformed, or expired leases fail before effects.
22. Authoritative root outage: both exact and different-source inputs fail retryably before campaign, Sheet, attachment, model, event, notification, queue, or reply work.
23. Pending-worker race: a worker may load an exact pending document, but if terminal Sent reconciliation commits and deletes it before the worker's transactional pre-send claim, the worker performs zero Graph calls; an active or malformed pending-send lease is never stolen.
24. Pending stage-after-claim race: worker A claims exact pending work, terminal staging commits before A's final Graph fence, and A releases only its own claim with zero Graph calls; a stale token cannot clear replacement work.
25. Sheet attempt concurrency: owner A persists `request_started`; owner B may not issue a second Sheet mutation and may finalize only after exact row-plus-note readback records `reconciled_applied`. Malformed, partial, absent, or unreadable attempt/evidence fails closed and operator-visible.
26. Stale finalizer: after B acquires a higher canonical fence, A's Firestore finalization transaction performs zero writes; B alone may reconcile and finalize.
27. Ambiguous cleanup: apply-then-raise is accepted only when every planned exact root, canonical claim, current obligation, active pointer, and immutable settlement projection verifies.
28. Cleanup-before-marker retry: after successful cleanup but before processed-marker persistence, the exact source matches the settlement projection and exits without replacement, model, Sheet, notification, queue, or reply effects.
29. Definite-429 lineage: owner A records `definitely_not_applied`; A cannot create another attempt, while different owner B with a higher fence creates exactly one linked ordinal. Timeout/5xx ambiguity never creates a second attempt.
30. Multiple settlement generations: A settles and cleans up, B legitimately stages with a fresh ordinal-one Sheet attempt and settles independently, both tombstones remain exact-source routable, and retries of A and B perform zero save/model/Sheet/send work. A ninth generation fails closed without evicting history.
31. Partial terminal-marker matrix: every active marker shape blocks both the early pending claim and the final pre-Graph fence, releases only the exact owned claim when needed, and produces zero Graph calls; historical outcomes/settlements remain non-blocking.
32. Sheet attempt v2 integrity: stale full hashes, recomputed missing/extra/cross-status shapes, invalid values/types/timestamps/fences, v1 active/history/tombstone state, duplicate IDs, non-increasing fences, and immutable-hash lineage links all fail closed.
33. Sheet transition matrix: every pair of statuses is exercised, only the two documented transition families succeed, exact same-state replay writes nothing, terminal states cannot be rewritten, and review-to-reconciliation strips old outcomes.
34. Attempt transaction readback: exact apply-then-raise is accepted, while no-apply and a different internally hash-valid fabricated state remain retryable for both attempt creation and outcome persistence.
35. Review and idempotency: review binds the post-transition full hash and rotates once, exact replay is a no-op, applied/reconciled execution performs no provider or readback work, and finalization rejects invalid nested lineage before writes.
36. Mutation-kind geometry: finalization and settlement validation reject fully rehashed attempts and projections whose valid-enum mutation kind disagrees with the saga's immutable source/final-row relationship.
37. Attempt-creation no-apply replay: the first wrapper invocation remains retryable with no attempt/history/review or provider call, and a second exact invocation can create and apply its attempt without poisoned state.
38. Pre-provider geometry fence: a wrong valid caller kind and a staged saga carrying mutable `finalRow` drift both produce zero provider calls and persist no attempt or review.

## Non-Goals

- redesigning all campaign state transitions;
- changing model prompts or OpenAI behavior;
- deploying to production;
- running provider calls or sending mail;
- solving unrelated row-shift, completion, or notification behavior unless a required regression exposes it as part of this exact invariant.
